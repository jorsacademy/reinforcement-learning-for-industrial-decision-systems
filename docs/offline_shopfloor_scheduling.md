# Offline Dynamic Shop-Floor Dispatching

This benchmark studies production dispatching from fixed historical shop-floor logs.

It is intentionally different from the repository owner's separate online scheduling projects:

- the JSSP project trains PPO by interacting with a schedule-generation environment;
- the automotive paint-shop project trains an online hyper-heuristic policy in a dynamic simulator;
- this benchmark does not allow the learned selector to interact with the simulator during fitting.

## Shop model

The benchmark uses a single shared machine with:

- stochastic job arrivals;
- job-specific processing times;
- due dates;
- priority weights;
- product families;
- sequence-dependent family changeover time.

At every machine-release decision, the action is one dispatching rule:

```text
FIFO
EDD
SPT
ATC
```

The chosen rule selects the next job from the currently released queue.

This fixed action space makes historical rule-selection logs practical even when queue length and job identities change over time.

## Operational objective

The episode cost combines:

```text
priority-weighted tardiness
+ setup-time cost
+ flow-time cost
```

Held-out evaluation also reports each KPI separately, including on-time completion rate.

## Historical behavior policy

Logged trajectories are generated by a legacy rule selector with limited random rule variation.

The offline learners receive only:

```text
state features
selected dispatch rule
reward
next state
terminal flag
```

They do not receive future arrivals or hidden simulator information.

## State representation

The fixed-size state summarizes the current queue and machine context:

- queue length;
- queued workload;
- mean and minimum processing time;
- mean and minimum slack;
- overdue-job ratio;
- same-family opportunity;
- mean priority weight;
- current production time.

## Classical dispatching rules

FIFO prioritizes arrival order.

EDD prioritizes earliest due date.

SPT prioritizes shortest processing time.

ATC uses an apparent-tardiness-cost priority index balancing urgency, weight, and processing time.

All four fixed rules are retained as explicit Industrial Engineering baselines.

## Rolling-horizon local permutation search

A model-based reference enumerates short permutations of currently released candidate jobs.

It evaluates local sequence cost under known processing times, due dates, priorities, and setup times, then dispatches using a rule that reproduces the selected first job when possible.

Future arrivals are not known to this reference.

It is therefore described as rolling-horizon local search, not a global scheduling optimum.

## Offline behavior cloning

A neural classifier learns the historical rule-selection policy from logged states and actions.

This creates both a behavior-cloning baseline and a behavior-probability model used for support diagnostics.

## Conservative offline DQN

The offline Q learner uses a discrete CQL-style objective:

```text
TD loss
+ alpha * (logsumexp Q(s,a) - Q(s,a_logged))
```

The learner trains entirely from the fixed transition table.

## Behavior-support guard

The support guard checks the behavior-cloning model's estimated probability of the learned target action.

If that probability is below a declared threshold, the action is replaced by the behavior model's most likely dispatch rule.

The intervention rate is reported separately so a guarded result is not credited entirely to the learned policy.

## Fitted Q Evaluation

A neural FQE model estimates each frozen target policy from logged transitions before simulator testing.

FQE is interpreted together with behavior-support diagnostics because weakly supported rule choices can produce unreliable counterfactual estimates.

## Evaluation

Policies are frozen before held-out simulation.

Reported metrics include:

- mean composite operational cost;
- p90 cost;
- priority-weighted tardiness;
- setup time;
- mean flow time;
- on-time completion rate;
- target-action behavior support;
- FQE-estimated cost;
- support-guard intervention rate.

## Scope

This is a synthetic dynamic dispatch benchmark, not a factory scheduling deployment.

A production implementation would require calibrated arrival processes, processing times, setup matrices, due-date policies, job priorities, shift calendars, machine availability, and MES/APS integration.
